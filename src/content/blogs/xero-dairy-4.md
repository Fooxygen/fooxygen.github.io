欢迎回到 Xero。模块与包的实现早在 10 月份就已经落地，但单独拎出来讲总觉得缺一些实质性演示，因此我在此基础上添加结构体与常量的基础功能，并借此推动标准库的设计，下面来介绍模块与包的架构设计。

## 目录即 Package，文件即 Module

我选择 Python 的设计方式，主要考虑是文件目录即包和模块的组织形式，非常清晰。Xero 的 Package 指的是根目录具备 `xero.package.toml` **包配置文件**的目录，而子目录不叫做包，而直接体现为命名空间划分，无需独立的配置文件。每个 Xero 源代码文件就是一个模块。

引入一个包时，仅需在**项目配置文件**的 `packages` 字段填写根目录的路径。目前仅解析其中的包配置文件和 Xero 源代码文件，其余文件将被忽略。

```
xero/
├── xero.package.toml       # package configuration file
├── math.xe                 # xero::math
├── math/
│   └── linalg.xe           # xero::math::linalg
├── io/
│   ├── file.xe             # xero::io::file        (placeholder)
│   └── console.xe          # xero::io::console     (placeholder)
└── str.xe                  # xero::str
```

进入代码后，包和模块共同构建出一棵命名空间树，通过形如 `a::b::c` 路径表达式来逐层访问成员。例如标准库 `xero` 中的 `math` 数学库定义了部分基础函数，则可以通过 `xero::math::abs` 调用绝对值运算函数；还可以通过 `xero::math::pi` 使用 `pi` 常量。

> [!TIP]
> 个人认为**包**是形式上的结构，而**库**是功能上的集合，因此一般说标准库而不是标准包（好别扭）。

## 路径表达式

路径表达式是由多个字段表达的命名空间树的一条路径，通常末段是命名空间成员，其余段是命名空间，比如函数调用，常量访问，类型引用等等。

从根节点到某个子节点的书写形式是**完整访问路径**，但如果包和模块层级丰富，书写起来会很麻烦。因此我们可以使用 `use` 别名表达式，为部分路径设定别名，代替完整访问路径的某一段，形成**别名访问路径**。例如在模块顶层定义中使用 `use xero::math::linalg` 定义线性代数库的别名 `linalg`，不过目前只是默认使用末段作为别名，计划是可在后面追加 `as` 关键字以指定别名。

别名机制仅生效于其所在的模块。

```
use xero::math

const pi: f64 = 3.141592653589793;
fn main() {
    println(pi);
}
```

## 编译

每当处理一个模块，Xero 会先搜索其中的路径表达式，再进而搜索是否引入了相关的包，据此建立命名空间树结构。

### 符号

变化集中于**符号**上，因为这些类型、函数都有自己的归属命名空间，而不是堆在一个模块中，必须要予以可区分的名字。

没有模块与包机制时，FnScope 函数表只记录从符号到 Fn 的映射，TypeScope 类型表也只记录从符号到 Type 的映射。在命名空间的设计下，它们也同步改造为树结构，其中的节点仍然是它们自己的短符号，例如 `vec2`，`has_prefix`，但完整的符号应该分别是 `xero::math::linalg::vec2` 和 `xero::str::has_prefix`。

使用完整的符号最精确，但依旧是麻烦的。树结构的显著好处是可以直接写短符号，通过向上搜索父命名空间的方式定位到符号。例如 `linalg` 的函数想要使用定义在其父包 `math` 的函数时，直接书写函数名即可，除非是调用其它包的同名函数，这种机制和 C++ 嵌套命名空间是一致的。

在 IR 中，全部使用的是完整的符号以区分命名。

- 函数名由模块全名、函数名和参数列表拼接，例如 `xero::math::abs(f64)`；
- 方法用调用方类型的全名做前缀，例如 `xero::math::linalg::vec2::length()`；
- `main` 是唯一保留原名的特例；

LLVM 的符号表是平的，模块边界不会生成新的 LLVM Module，只体现在名字上，因此两个模块里的同名函数不会撞在一起。

### 尚未拆分的 LLVM Module

现在代码生成模块还是把所有 IR 写入一个 LLVM Module 中，仅输出一个 `.ll`。当仅有少数集中于一个模块的变更时，仍然要重新编译所有涉及到的模块，在代码庞大后将给编译效率带来阻碍。未来确定要进行的改造是**增量编译**，也就是把项目拆成稳定的编译单元，记录单元之间的依赖，再次编译时**只重新处理发生变化的单元，以及依赖它、确实受影响的单元**，其余单元**复用上一次的产物**。

## 标准库

`lib/xero` 是第一个用这套机制组织的真实代码。它本身就是一个普通包，根目录下具备包配置文件，子目录和 `.xe` 文件按前面的规则展开成命名空间。

目前大致分了几块，并列举已实现的功能类别：

- `xero::math`： 数学库的基础函数、常量；
- `xero::math::linalg`：线性代数库；
- `xero::str`：字符串查找、切分、拼接等；
- `xero::char`：字符分类；

```
# xero::math

# Constant

const eps: f64 = 0.000001;
const pi:  f64 = 3.141592653589793;
const e:   f64 = 2.718281828459045;

# Range

fn abs(x: i32) -> i32 { if (x < 0) { return -x; } return x; }
fn abs(x: i64) -> i64 { if (x < 0) { return -x; } return x; }
fn abs(x: f32) -> f32 { return @abs(x); }
fn abs(x: f64) -> f64 { return @abs(x); }
```

## 结构体与常量

结构体和常量是在模块与包之后添加的功能，涉及类型全名、字段布局、方法表，以及模块常量的编译期折叠。它们和模块机制有不少交叉，但本次 Blog 先不展开。

## 总结

本次主要讲了模块与包是怎么从目录和文件长成一棵命名空间树，以及符号在 Sema 和 IR 中的变化。至少现在模块和包机制初步构成，标准库也可以继续迭代了。
